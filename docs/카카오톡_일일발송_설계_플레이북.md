# 카카오톡 일일 자동발송 — 설계 플레이북

> **이 문서의 목적**: 지금은 구현하지 않는다. 나중에 "카카오톡으로 매일 자동 발송" 기능이 필요해졌을 때,
> **이 문서 하나만 보고 바로 착수**할 수 있도록 결정·근거·함정·사양을 동결해 둔 것이다.
>
> **적용 범위**: `asset_manager` 전용 문서가 아니다. §2~§7은 **앱과 무관한 공통 사양**이고,
> §8만 이 앱 전용 부록이다. 다른 앱에 붙일 때는 §7의 어댑터 계약만 새로 쓰면 된다.
>
> **조사·검증일**: 2026-08-08 (3개 AI 교차검토 + 공식 문서/저장소 코드 직접 확인).
> 시간이 지나 재확인이 필요한 항목은 **§9**에 따로 모아 두었다.

## 1. 결론 요약

1. **발송 채널**: 카카오 공식 **"나에게 보내기"** REST API. 사업자등록·검수·비용 전부 불필요.
2. **실행 환경**: 3지선다이며 **선택 기준은 앱 개수가 아니라 ① 시각 정밀도 ② 계산 복잡도 ③ 데이터 위치** 세 가지다 (§3).
3. **가장 큰 함정 3개**: OAuth 테스트 모드의 **7일 토큰 폐기**(§4-A), `portfolio.json`은 **압축 파일**이라 바로 파싱 불가(§8.1), 저장된 가격은 **오래된 값**일 수 있음(§8.2).

## 2. 발송 채널 — 결정 완료

| 방식 | 요건 | 비용 | 판정 |
|------|------|------|------|
| **나에게 보내기** (`/v2/api/talk/memo/default/send`) | 카카오 개발자 앱 등록 + `talk_message` 동의 | 무료 | ✅ **채택** |
| 친구에게 보내기 | 비즈 앱 전환 + 권한 심사 | 무료 | ❌ 본인 수신이면 불필요 |
| 알림톡 | **사업자등록 + 채널 + 템플릿 심사** | 건당 약 8원 | ❌ 개인 용도 부적합 |

**타인에게 보내야 할 때만** 알림톡으로 넘어간다. 본인 수신인 한 위 판정은 뒤집히지 않는다.

### 쿼터에 대한 정확한 표현

공식 쿼터 표는 메시지 API에 대해 `일 30,000건 / 발신자당 100건 / 수신자당 100건 / 발신자·수신자 pair당 20건`을 제시하지만, **대상을 구분하지 않는다.** 카카오 운영자는 devtalk에서 이 세부 제한이 **"'친구에게 메시지 보내기'에만 해당"**이라고 답변했다(2021년).

따라서 문서화할 표현은 다음 두 문장이다.

- 나에게 보내기에 **pair 20건 제한이 적용된다고 볼 근거는 부족하다.**
- 그렇다고 **"공식적으로 무제한"이라 단정해서도 안 된다** (운영자 답변은 2021년 자료이고 현재 표는 대상을 명확히 구분하지 않음).

**실무 규약**: 하루 총 발송을 **10건 이하**로 유지한다. 어느 해석이 맞든 안전하며, 앱별 개별 발송(앱 5개 = 5건)도 이 범위에 들어간다.

## 3. 실행 환경 — 3지선다

> ⚠️ **여기가 이 문서에서 가장 중요한 부분이다.** 흔한 오판은 "복잡한 계산이 필요하면 Cloud Run"인데,
> 이 저장소에서는 **반대이거나, 최소한 그렇게 단순하지 않다.**

### 3.1 판단을 뒤집는 사실 — 런타임 언어

이 저장소의 지표·신호 계산은 **`utils/`의 순수 TypeScript 함수**이고, 이미 **tsx로 Node에서 실행되고 있다**(`package.json`의 40여 개 `test:*` 파리티 스위트가 전부 그 증거다). 즉:

| 실행 환경 | 언어 | `utils/` 재사용 | 결과 |
|---|---|---|---|
| Google Apps Script | JavaScript | 번들 후 이식 가능 | 계산 로직 **재사용** |
| **기존** Cloud Run 백엔드 | **Python** (`main.py`) | **불가 — 전면 재작성** | 파리티 리스크 발생 |
| **신규** Node.js Cloud Run / Functions | TypeScript | `import`로 그대로 | 계산 로직 **재사용** |

**"복잡한 신호까지 계산해야 하니 (기존) Cloud Run"은 틀린 결론이다.** Python으로 옮기면 RSI·MA·터틀·클라이맥스 로직을 두 언어로 이중 관리하게 되고, 이 프로젝트의 명시된 교훈 — *"엔진 변경에는 골든 파리티 테스트가 필수"* — 에 정면으로 걸린다. 실제로 위성 ATR 사이징 버그가 8개 종목의 거래를 0건으로 만든 채 백테스트 전체를 통과한 전례가 있다.

복잡한 계산 + 정확한 시각이 **동시에** 필요하면 정답은 **선택지 C(신규 Node.js 서비스)**이지 B가 아니다.

### 3.2 선택지 비교

| | **A. Apps Script** | **B. 기존 Python Cloud Run 확장** | **C. 신규 Node.js Cloud Run** |
|---|---|---|---|
| 시각 정밀도 | **±15분** (`nearMinute`) | 분 단위 정확 | 분 단위 정확 |
| 1회 실행 제한 | **6분** | 사실상 없음 | 사실상 없음 |
| `utils/` 재사용 | 번들 후 가능 | **불가(재작성)** | **그대로 가능** |
| 백엔드 재배포 필요 | 없음 | **있음(사용자 책임)** | 신규 배포 1회 |
| Drive 접근 | 본인 계정, 단 **권한 넓어짐**(§8.4) | 저장된 토큰 재사용 | 저장된 토큰 재사용 |
| 7일 토큰 위험(§4-A) | **없음** | 있음 | 있음 |
| 재시도·감사로그·Secret Manager | 빈약 | 완비 | 완비 |
| 착수 비용 | 가장 낮음 | 중간 | 중상 |

**B를 권하지 않는 추가 근거**: 백엔드 Python 소스는 이 저장소에 없고 사용자가 직접 재배포해야 한다. 이게 실제 병목이라는 증거로, `/symbols` gzip과 `quotes_only` 최적화가 지금도 "재배포 대기" 상태로 남아 있다(RULES.md §14). B는 이 대기열에 항목을 하나 더 얹는 선택이다.

### 3.3 결정 순서도

질문 4개에 답하면 환경이 결정된다.

1. **분 단위로 정확한 시각이 필요한가?** (예: 정확히 09:00 개장 알림, 15:40 마감 직후)
   → 예: **C** (또는 A + Cloud Scheduler 트리거 조합) / 아니오: 계속
2. **보낼 정보가 L3 등급인가?** (§8.2의 등급 정의 — 최신 시세 + 앱과 동일한 신호 재계산)
   → 예: **C** / 아니오: 계속
3. **대상 앱의 데이터가 Firestore·DB·보호된 API에 있는가?**
   → 예: **C** / Drive·Sheets·공개 API: 계속
4. → **A (Apps Script)**

**어느 경우에도 B(기존 Python 백엔드 확장)는 1순위가 아니다.**

## 4. 착수 전 확인 체크리스트

구현을 시작하기 **전에** 아래 4개를 확정한다. 이게 안 되면 잘못된 환경을 골라 되돌리게 된다.

### A. ⚠️ GCP OAuth 동의 화면의 게시 상태

**가장 중요하다.** Google은 다음 세 조건이 모두 맞으면 리프레시 토큰을 **7일 후 폐기**한다.

- 사용자 유형이 **외부(External)**
- 게시 상태가 **테스트(Testing)**
- 요청 범위가 이름·이메일·프로필만이 아님 → **이 앱은 `drive.file`을 요청하므로 예외에 해당하지 않는다**

즉 게시 상태가 "테스트"라면 **선택지 B·C의 무인 작업은 매주 죽는다.** 지금까지 이 문제를 못 느꼈을 수 있는데, 사람이 직접 쓸 때는 JWT가 30일이고 필요하면 다시 로그인하기 때문이다. **무인화하는 순간에만 드러나는 함정이다.**

- **확인**: GCP 콘솔 → API 및 서비스 → OAuth 동의 화면 → 게시 상태
- **해결**: "프로덕션"으로 게시. `drive.file`은 Google이 **민감하지 않은 범위**로 분류하므로 게시·검증 부담이 전체 `drive`보다 낮다.
- **선택지 A는 이 문제와 무관하다** (본인 계정에서 본인 스크립트를 실행하는 구조).

### B. 발송 시각 정밀도 — "8시 반쯤"인가 "정확히 9시"인가
±15분이 허용되면 A가 열린다. 아니면 C다.

### C. 보낼 정보의 등급 — §8.2의 L1/L2/L3 중 어디까지인가
이게 작업량을 가장 크게 좌우한다.

### D. 다른 앱들의 데이터 위치
앱 개수가 아니라 **위치**가 기준이다. Drive/Sheets/공개 API면 A로 충분하고, DB·보호된 API면 C다.

## 6. 공통 규약 (어느 런타임을 골라도 동일)

### 6.1 토큰 수명

| 항목 | 값 |
|---|---|
| 액세스 토큰 (REST API) | **6시간** (Android/iOS 12h, JS SDK 2h — 혼동 주의) |
| 리프레시 토큰 | **2개월** |
| 리프레시 토큰 갱신 가능 시점 | 만료까지 **1개월 미만** 남았을 때 |

**운영 규약**: 매 실행마다 리프레시 토큰으로 액세스 토큰을 새로 받는다. 갱신 응답에 **새 리프레시 토큰이 포함되어 있으면 반드시 저장값을 교체**한다. 매일 실행하면 갱신이 계속 일어나므로 사실상 영구 무인 운영이 된다.

> ⚠️ **락아웃 위험**: 새 리프레시 토큰을 받았는데 **저장에 실패**하면, 기존 토큰이 폐기된 뒤라 다시 브라우저 인증을 해야 한다.
> → **저장 성공을 확인한 뒤에만** 발송 단계로 진행하고, 저장 실패는 반드시 실패 알림(§6.5) 대상으로 삼는다.

### 6.2 메시지 200자 규약

기본 텍스트 템플릿은 **최대 200자**다. 대응 방식 3가지:

1. **앱당 1건 분할 발송** (권장 — 하루 10건 이하면 쿼터 안전)
2. 전체를 200자 이내로 압축해 1건
3. 짧은 요약 + `[자세히 보기]` 버튼 → 전체 보고서는 웹에서

버튼 링크는 GitHub Pages에 올린 앱 URL을 그대로 쓰면 된다.

### 6.3 중복 발송 방지 (멱등)

스케줄러는 **at-least-once**다. 드물게 같은 작업이 두 번 실행된다. 트리거 종류와 무관하게 필요하다.

- **멱등 키**: `YYYY-MM-DD + 발송종류` (예: `2026-08-08:asset-daily`)
- 발송 **전에** 키를 기록하고, 이미 있으면 건너뛴다.
- 저장 위치: A → `PropertiesService` / B·C → Firestore

### 6.4 비밀값 보관

| 값 | A (GAS) | B·C (Cloud Run) |
|---|---|---|
| 카카오 REST 키 / 리프레시 토큰 | `PropertiesService` (스크립트 속성) | Secret Manager |
| 서버용 Gemini 키 (쓸 경우) | `PropertiesService` | Secret Manager |

**코드·저장소에 절대 하드코딩하지 않는다.** 이 저장소는 GitHub 공개 배포(Pages)를 하므로 특히 그렇다.

### 6.5 실패 알림

무인 작업의 실패는 **조용히 일어난다.** 최소한 다음은 넣는다.

- 발송 실패 / 토큰 갱신 실패 / 데이터 로드 실패 시 → 본인 이메일 알림 (A는 `MailApp`, B·C는 Cloud Logging + 알림 정책)
- **2일 연속 미발송이면 이상 신호**로 간주할 수 있게, 성공 시각도 함께 기록한다.

## 7. 앱 어댑터 계약 — 다른 앱을 붙이는 방법

발송기는 **하나만** 만든다. 앱마다 **수집기(어댑터)** 하나씩 추가하는 구조다. 새 앱 편입 시 카카오 인증·스케줄·멱등 로직은 건드리지 않는다.

### 7.1 공통 데이터 계약

```ts
interface DailySummary {
  appId: string;        // 'asset-manager' 등 고유 식별자
  appName: string;      // 메시지에 표시될 이름
  asOf: string;         // 데이터 기준 시각 (ISO). ⚠️ 실행 시각이 아니라 '데이터가 만들어진 시각'
  lines: string[];      // 핵심 항목 3~5개. 각 줄은 짧게
  alert?: string;       // 있으면 강조 표시
  url?: string;         // '자세히 보기' 버튼 대상
  stale?: boolean;      // 데이터가 오래됐으면 true → 메시지에 경고 표기
}
```

`asOf`와 `stale`을 계약에 넣은 이유는 §8.2 때문이다. **"오래된 값을 오늘 값처럼 보내는 것"이 이 시스템에서 가장 위험한 실패 모드**이므로, 계약 수준에서 막는다.

### 7.2 어댑터 규칙

- 어댑터는 **읽기 전용**이다. 어떤 앱의 데이터도 수정하지 않는다.
- 어댑터 하나가 실패해도 **나머지는 발송된다** (부분 성공 허용). 실패한 앱은 "○○ 수집 실패" 한 줄로 대체한다.
- 어댑터는 **200자 규약을 모른다.** 잘라내기·포맷은 공통 코어의 책임이다.

### 7.3 런타임별 책임 분리

같은 코드를 GAS와 Node에서 그대로 돌릴 수는 없다(API가 다르다). 다음처럼 나눈다.

| 계층 | 내용 | 이식성 |
|---|---|---|
| **공통 (순수 함수)** | 요약 계산, 200자 분할, 메시지 포맷, 멱등 키 생성 | 그대로 이식 |
| **A 전용** | `DriveApp`, `UrlFetchApp`, `PropertiesService`, `MailApp` | 교체 필요 |
| **B·C 전용** | HTTP 서버, Firestore, Secret Manager | 교체 필요 |

공통 계층을 순수 함수로 유지하면 A → C 이관 비용이 낮아진다. **이게 A로 시작해도 되는 이유다.**

### 7.4 새 앱 편입 체크리스트

- [ ] 그 앱의 데이터가 **무인 접근 가능한 위치**에 있는가? (브라우저 localStorage에만 있으면 **불가** — 먼저 서버나 Drive로 내보내야 함)
- [ ] 인증이 필요한가? 필요하면 그 토큰도 §6.1과 같은 회전 규약이 있는가?

## 8. 부록 — `asset_manager` 전용 사항

> 다른 앱에 적용할 때는 이 절 전체를 무시하고, 그 앱에 맞는 부록을 새로 쓴다.

### 8.1 `portfolio.json`은 일반 JSON이 아니다

저장 직전에 **LZ-String으로 압축**된다.

```
services/googleDriveService.ts:420   LZString.compressToUTF16(content)
services/googleDriveService.ts:421   new Blob([compressed], { type: 'application/json' })
```

파일을 읽어서 바로 `JSON.parse()` 하면 **실패한다.** 반드시 `decompressFromUTF16()`을 먼저 통과시켜야 한다.

**문자 인코딩 라운드트립 분석** (구현 전에 알아둘 것):
`compressToUTF16`의 출력 문자 코드 범위는 `[32, 32799]`이고, 서로게이트 영역(0xD800=55296) **아래**라 lone surrogate가 생기지 않는다. `Blob`은 이 문자열을 UTF-8로 인코딩해 업로드하므로, 읽을 때 **UTF-8로 디코딩하면 원래 문자열이 복원**된다(GAS라면 `getBlob().getDataAsString('UTF-8')`). 이론상 안전하지만, **구현 첫 단계에서 실제 파일로 라운드트립을 반드시 확인**한다(§10-2).

라이브러리는 `lz-string@^1.5.0`으로 이미 의존성에 있고, 순수 JS라 GAS에 그대로 넣을 수 있다.

**대안**: 앱이 자동화 전용 **비압축 요약 파일**을 따로 저장하게 만드는 방법도 있다. 다만 이건 앱 코드 변경이고, "보이지 않는 쓰기 금지" 규칙에 걸리므로 **명시적 사용자 동작이나 opt-in 설정**을 동반해야 한다.

### 8.2 저장된 가격은 최신이 아니다 — 정보 등급 L1/L2/L3

`portfolio.json`에는 **마지막으로 앱을 열었을 때의 가격**이 들어 있다. 며칠 안 열었으면 그만큼 오래된 값이다. 보낼 정보를 아래 3등급으로 나눠 판단한다. **작업량이 등급마다 자릿수 단위로 다르다.**

| 등급 | 내용 | 필요한 것 | 적합 환경 |
|---|---|---|---|
| **L1** | 보유 종목 수, 매수 기준 금액, 계좌·버킷 구성, 미처리 액션 큐 건수 | Drive 파일 읽기 + 압축 해제만 | **A** (반나절) |
| **L2** | 총자산, 전일 대비 변동, 수익률 상·하위 종목 | + 시세/환율 API 호출 + 평가액 재계산 | **A** (1~2일) |
| **L3** | RSI·MA·터틀 신호·급성 매도경보 등 **앱 화면과 동일한 신호** | + `utils/` 지표 엔진 이식 + 파리티 검증 | **C** (또는 A, 6분 제한 확인 필요) |

**L1은 `asOf`만 정직하게 붙이면 오래된 값이어도 무해하다.** L2부터는 반드시 최신 시세를 가져와야 하고, `stale` 플래그가 의미를 갖는다.

**L3 착수 전 필수**: 앱과 다른 값을 보내면 신뢰가 무너진다. 이식 후 **골든 파리티 테스트**(`tests/*Parity.ts` 방식, 명시적 절대값 고정)를 반드시 붙인다. 경로 A와 경로 B를 비교하는 자기참조적 테스트는 금지다(RULES.md §13).

### 8.3 재사용 가능한 계산 자산

| 대상 | 재사용 | 비고 |
|---|---|---|
| `utils/*.ts` (순수 함수) | ✅ 가능 | `buildEnrichedIndicator`(MA/RSI/ATR/52주/디스트리뷰션), `climaxFlags`, `turtlePositionView` 등. 이미 tsx로 Node 실행 중 |
| `hooks/*.ts` | ❌ 불가 | React 의존. 필요한 로직은 순수 함수로 추출한 뒤 사용 |
| `services/*.ts` | △ 부분 | HTTP 호출부는 런타임별 fetch로 교체 필요 |
| Cloud Run `/history`, `/`, `/exchange-rate` | ✅ 가능 | 무인 작업에서도 그대로 호출 가능 (인증 불필요) |

### 8.4 Drive 권한이 오히려 넓어진다 (선택지 A의 대가)

현재 앱은 **최소 권한인 `drive.file`**을 요청한다(`services/googleDriveService.ts:132`). 이건 "그 OAuth 클라이언트가 만든 파일"에만 접근하는 범위다.

- **B·C**: 백엔드가 보관 중인 **같은 클라이언트의** 리프레시 토큰을 쓰므로, `portfolio.json`을 읽는 데 **추가 권한이 필요 없다.** 즉 Cloud Run 방식의 장애물은 권한이 아니라 **코드가 없다는 것**뿐이다.
- **A**: GAS의 `DriveApp`으로 **다른 앱이 만든 기존 파일**을 검색·조회하려면 통상 `drive.readonly` 또는 전체 `drive` 승인이 필요하다. GAS 문맥의 `drive.file`은 "그 스크립트가 만든 파일"을 뜻해서 `portfolio.json`을 찾지 못한다.
  → **완화책**: `appsscript.json`에 `drive.readonly`를 명시해 **읽기 전용으로 제한**한다. 전체 `drive`보다 낫다. 본인 전용 스크립트라면 수용 가능한 수준이지만, **현재 앱보다 권한이 넓어진다는 사실 자체는 기록해 둔다.**

> 참고: README에는 "공유 폴더: 전체 `drive` scope 사용"이라 적혀 있으나 **실제 코드는 `drive.file`**이고, `config/constants.ts:38`의 `GOOGLE_OAUTH_SCOPES`(전체 `drive`)는 **어디서도 import되지 않는 죽은 상수**다. 이 불일치는 별도 작업으로 분리했다.

### 8.5 Gemini 키는 서버에서 쓸 수 없다

키는 **브라우저 localStorage 전용**이며, Drive 동기화 payload에서도 의도적으로 제외된다(`services/geminiSettings.ts:5`의 경고 주석). 따라서 무인 작업에서 AI 요약을 쓰려면 **별도의 서버용 키**를 §6.4 위치에 새로 넣어야 한다.

**권장**: 초판은 **AI 없이 규칙 기반**으로 만든다. 숫자를 AI에 계산시키면 검증이 불가능해진다. AI는 이미 확정된 숫자에 **자연어 설명을 붙이는 용도로만** 나중에 추가한다.

## 10. 착수 시 구현 순서

**각 단계가 끝날 때마다 다음 단계로 갈지 재판단한다.** 특히 2단계 결과가 나쁘면 환경 선택을 되돌린다.

1. **고정 문구 발송 성공** — 카카오 인증 1회 + 하드코딩된 "테스트" 문자열 발송. 여기까지가 전체의 절반이다.
2. **압축 파일 읽기 검증** — `portfolio.json`을 읽어 `decompressFromUTF16` → `JSON.parse` 성공 확인 (§8.1). **실패하면 환경 선택을 재검토한다.**
3. **L1 요약 1건** — 최신 시세가 필요 없는 항목만. `asOf` 표기 포함.
4. **멱등 + 실패 알림** — §6.3, §6.5. 무인화 전에 반드시.
5. **L2로 확장** — 시세·환율 호출 추가.
6. **다른 앱 어댑터 추가** — §7.4 체크리스트.
7. **L3가 필요하면** — 실행 시간·계산량 평가 후 A 유지 또는 C 이관 결정. 파리티 테스트 필수.

**예상 소요**: 1~3단계는 L1 기준 반나절~1일. **단 §8.1 압축 해제와 §8.2 정보 등급에 따라 커질 수 있다** — "반나절"은 L1에서만 유효한 숫자다.

- ⚠️ 기존 백엔드는 **Python** → `utils/` 재작성 = 파리티 리스크 (§3.1)
- ⚠️ GAS는 **±15분·6분 제한** (§3.2)
- ⚠️ GAS `DriveApp`은 **권한이 넓어짐** → `drive.readonly`로 제한 (§8.4)
- ⚠️ Gemini 키는 **브라우저 전용** → 서버용 키 별도 필요 (§8.5)
- ⚠️ localStorage에만 데이터가 있는 앱은 **자동화 불가** → 먼저 서버·Drive로 내보내기 (§7.4)
